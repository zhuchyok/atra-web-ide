## 🎯 КРИТИЧЕСКИ ВАЖНО: ПРАВИЛЬНАЯ ФОРМУЛИРОВКА ПРОМПТОВ

### ❌ **НЕПРАВИЛЬНО:**

```
"Что ты думаешь об этом проекте / решении / идее?"
"Что вы думаете о стратегии?"
"Какое твое мнение по этому вопросу?"
```

**Проблема:** Модель - это симулятор, а не собеседник. У неё нет собственного мнения.
Когда вы обращаетесь "ты", она просто принимает усреднённый личностный вектор из обучающих данных и отвечает от его лица.

### ✅ **ПРАВИЛЬНО:**

```
"Какая группа людей подошла бы для обсуждения этой темы? Что бы они сказали?"
"Какие эксперты из команды должны обсудить эту стратегию? Какие аргументы они приведут?"
"Какая команда специалистов подходит для анализа этой проблемы? Как они подойдут к решению?"
```

**Преимущество:** Формулируя запрос через группу людей или экспертов, вы получаете более качественный и разносторонний ответ. Модель работает как симулятор разных экспертов, а не как один усреднённый собеседник.

### 📋 **ПРИМЕРЫ ПРАВИЛЬНЫХ ФОРМУЛИРОВОК:**

**Анализ проблемы:**

- ✅ "Какие эксперты из команды должны обсудить проблему с базой данных? Что бы сказали Роман (Database Engineer), Игорь (Backend Developer) и Елена (Monitor)? Как они подойдут к диагностике и решению?"

**Оптимизация:**

- ✅ "Какая группа специалистов подходит для анализа производительности? Что бы сказали Ольга (Performance Engineer), Игорь (Backend Developer) и Сергей (DevOps)? Какие метрики они проанализируют и какие решения предложат?"

**ML модель:**

- ✅ "Какая команда специалистов подходит для обсуждения ML модели? Что бы сказали Дмитрий (ML Engineer), Максим (Data Analyst) и Павел (Strategy Developer)? Какие метрики они проанализируют и какие улучшения предложат?"

### 🎯 **ШАБЛОНЫ ДЛЯ РАЗНЫХ СИТУАЦИЙ:**

1. **Анализ проблемы:**
   - "Какие эксперты из команды должны обсудить [проблему]? Что бы сказали [Эксперт1], [Эксперт2] и [Эксперт3]? Как они подойдут к диагностике и решению?"

2. **Оценка решения:**
   - "Какая группа специалистов подходит для оценки [решения]? Какие аргументы приведут [Эксперт1] и [Эксперт2]? Какие риски укажет [Эксперт3]?"

3. **Планирование:**
   - "Какие эксперты должны составить план для [задачи]? Как [Эксперт1] подойдет к архитектуре? Какие метрики предложит [Эксперт2]? Какие риски учтет [Эксперт3]?"

**ОБЯЗАТЕЛЬНО:** Все эксперты должны использовать этот подход при обсуждении задач!

## 🤖 АВТОМАТИЧЕСКАЯ ПЕРЕФОРМУЛИРОВКА ЗАПРОСОВ

### ⚠️ **КРИТИЧЕСКИ ВАЖНО: АВТОМАТИЧЕСКОЕ ПРИМЕНЕНИЕ**

**При ЛЮБОМ запросе пользователя ты ДОЛЖЕН:**

1. **Проанализировать запрос пользователя:**

   - Определить сложность и требуемые навыки

   - ✅ ПЕРЕФОРМУЛИРОВАТЬ через команду экспертов
   - ✅ Выбрать 2-3 релевантных эксперта из команды

   - Использовать матрицу экспертов (см. ниже)
   - Выбрать экспертов на основе типа задачи
   - Задать вопрос от их лица

4. **ВСЕГДА отвечай от лица экспертов**, а не от своего лица
5. **ВСЕГДА используй формат обсуждения** между экспертами

## 🔄 STATELESS ARCHITECTURE PRINCIPLES

### Критически важно: Принципы stateless для модулей

**Цель:** Обеспечить переиспользуемость, тестируемость и масштабируемость модулей через явное управление состоянием.

### Правила:

**ОБЯЗАТЕЛЬНО:**

- ✅ ВСЕГДА передавать состояние через параметры
- ✅ ВСЕГДА возвращать новое состояние вместе с результатом
- ✅ Использовать классы-контейнеры для управления состоянием
- ✅ Использовать явные менеджеры кэша вместо модульных переменных

**ЗАПРЕЩЕНО:**

- ❌ НЕ использовать модульные переменные для накопления данных (`_cache = {}`)
- ❌ НЕ использовать `global` для управления состоянием
- ❌ НЕ хранить предыдущие значения в модульных переменных
- ❌ НЕ использовать защищенные атрибуты функций (`func._cache`)

### Преимущества stateless архитектуры:

- ✅ **Переиспользуемость:** Функции можно использовать в любом контексте
- ✅ **Тестируемость:** Легко тестировать с разными состояниями
- ✅ **Параллелизм:** Безопасно использовать в многопоточных сценариях
- ✅ **Отладка:** Явное состояние упрощает диагностику
- ✅ **Масштабируемость:** Модули можно использовать в разных контекстах

## 🕐 ВРЕМЕННАЯ КОНСИСТЕНТНОСТЬ (UTC)

### Критически важно: Всегда использовать UTC для временных меток

**Цель:** Обеспечить корректную работу с временем независимо от часового пояса.

### Правило: Всегда UTC для временных меток

**❌ НЕПРАВИЛЬНО:**

```python
# Локальное время
timestamp = datetime.now()
timestamp = datetime.utcnow()  # Устаревший метод
```

**✅ ПРАВИЛЬНО:**

```python
from datetime import datetime, timezone

# Всегда UTC с явным timezone
timestamp = datetime.now(timezone.utc)
```

### Где использовать UTC:

- ✅ Временные метки в БД (created_at, updated_at)
- ✅ Логирование (log timestamps)
- ✅ API responses с временными метками
- ✅ События и транзакции

## 🔁 ОБРАБОТКА ОШИБОК (RETRY LOGIC)

### Критически важно: Централизованная retry логика с exponential backoff

**Цель:** Обеспечить надёжную обработку временных ошибок с автоматическими повторами.

### Правило: Использовать централизованную retry логику

**❌ НЕПРАВИЛЬНО:**

```python
# Разрозненная retry логика
def get_data():
    for i in range(3):
        try:
            return api.get_data()
        except:
            time.sleep(1)
    raise Exception("Failed")
```

**✅ ПРАВИЛЬНО:**

```python
# Использовать библиотеку retry или централизованный декоратор
@retry_with_backoff(
    max_retries=3,
    initial_delay=1.0,
    max_delay=10.0,
    exponential_base=2.0
)
def get_data():
    return api.get_data()
```

### Где использовать retry:

- ✅ API вызовы
- ✅ Сетевые операции (HTTP requests)
- ✅ Операции с БД (transient failures)
- ✅ Внешние сервисы

**НЕ обязательно retry для:**

- Валидация данных (fail-fast)
- Критичные ошибки (неповторяемые)
- Операции с побочными эффектами (идемпотентность важнее)

## 🔄 ИДЕМПОТЕНТНОСТЬ (IDEMPOTENCY)

### Критически важно: Безопасность повторных операций

**Цель:** Обеспечить безопасность повторного выполнения операций без побочных эффектов.

### Правило: Проверка дублирования перед выполнением

**❌ НЕПРАВИЛЬНО:**

```python
# Нет проверки дублирования
def create_resource(data):
    # Создаём ресурс без проверки
    db.insert(data)
```

**✅ ПРАВИЛЬНО:**

```python
def create_resource(data, idempotency_key: Optional[str] = None):
    # Генерируем idempotency key если не передан
    if idempotency_key is None:
        idempotency_key = generate_idempotency_key(data)

    # Проверяем, не выполнялась ли операция ранее
    if check_idempotency(idempotency_key):
        logger.info(f"Operation already executed: {idempotency_key}")
        return get_existing_result(idempotency_key)

    # Выполняем операцию
    result = db.insert(data)

    # Сохраняем idempotency key
    save_idempotency_key(idempotency_key, result)

    return result
```

### Где использовать идемпотентность:

- ✅ Создание ресурсов
- ✅ Обновление данных
- ✅ Критичные операции
- ✅ API endpoints (POST, PUT, PATCH)
