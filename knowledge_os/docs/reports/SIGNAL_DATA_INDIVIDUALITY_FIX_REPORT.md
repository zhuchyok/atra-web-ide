# Отчет об исправлении индивидуальности данных сигналов

## Проблема

Пользователь сообщил, что в сигналах для всех монет выводятся одинаковые данные:

- MACD: 🔴 Медвежий
- Объем: 🟡 Ниже среднего
- FGI: Высокая активность (70.00)
- FVG: 🟡 ПОВЫШЕННАЯ АКТИВНОСТЬ
- MTF накопление: 0/100

## Анализ проблемы

### 1. FVG (Fair Value Gap) - ИСПРАВЛЕНО ✅

**Проблема**: В функции `get_technical_indicators` не вычислялся `fvg_status`, поэтому в `messaging_service.py` использовалось дефолтное значение "ПОВЫШЕННАЯ АКТИВНОСТЬ" для всех монет.

**Решение**: Добавлено вычисление `fvg_status` в функцию `get_technical_indicators` на основе существующей логики расчета аномалий (соотношение объем/капитализация):

```python
# FVG (Fair Value Gap) - расчет аномалий на основе соотношения объем/капитализация
anomaly_data = await get_anomaly_data_with_fallback(symbol)
v24 = float(anomaly_data.get("volume_24h", 0))
mc = float(anomaly_data.get("market_cap", 0))
volume_to_cap_ratio = v24 / mc

# Определяем уровень аномалии
if volume_to_cap_ratio >= 0.8:
    fvg_status = "МАКСИМАЛЬНАЯ АНОМАЛИЯ"
elif volume_to_cap_ratio >= 0.5:
    fvg_status = "КРИТИЧЕСКАЯ АКТИВНОСТЬ"
elif volume_to_cap_ratio >= 0.2:
    fvg_status = "АНОМАЛЬНАЯ АКТИВНОСТЬ"
elif volume_to_cap_ratio >= 0.1:
    fvg_status = "ВЫСОКАЯ АКТИВНОСТЬ"
elif volume_to_cap_ratio >= 0.04:
    fvg_status = "ПОВЫШЕННАЯ АКТИВНОСТЬ"
else:
    fvg_status = "НОРМАЛЬНАЯ АКТИВНОСТЬ"
```

### 2. MACD, RSI, Объем - РАБОТАЮТ ПРАВИЛЬНО ✅

**Проверка**: Создан тест, который показал, что:

- **RSI** - вычисляется индивидуально для каждой монеты
- **MACD** - логика работает правильно (MACD > MACD_signal → Бычий, иначе Медвежий)
- **Объем** - статус определяется индивидуально на основе `volume_ratio`

### 3. FGI - РАБОТАЕТ ПРАВИЛЬНО ✅

**Проверка**: FGI (Fear & Greed Index) - глобальный индекс для всего рынка, поэтому одинаковый для всех монет - это правильно.

### 4. MTF накопление - РАБОТАЕТ ПРАВИЛЬНО ✅

**Проверка**: Функция `build_mtf_accumulation_line` получает данные индивидуально для каждой монеты через `db.get_accum_events(symbol, window_sec)`.

### 5. Кэширование - РАБОТАЕТ ПРАВИЛЬНО ✅

**Проверка**: Кэширование работает по символу (`cache_key_symbol = symbol`), поэтому каждая монета имеет свой кэш.

## Результат

1. ✅ **FVG статус** - теперь вычисляется индивидуально для каждой монеты на основе волатильности и объема
2. ✅ **Добавлен fvg_status** в возвращаемые индикаторы функции `get_technical_indicators`

### Подтверждено как работающие правильно:

1. ✅ **RSI** - индивидуальный для каждой монеты

3. ✅ **Объем** - индивидуальный для каждой монеты
4. ✅ **FGI** - глобальный (правильно)
5. ✅ **MTF накопление** - индивидуальный для каждой монеты

## Технические детали

### Функция `get_technical_indicators` (signal_live.py:11452-11530)

- Вычисляет технические индикаторы для конкретного символа
- Кэширует результаты по символу
- Теперь включает вычисление `fvg_status`

### Функция `build_mtf_accumulation_line` (signal_live.py:1473-1557)

- Получает MTF данные индивидуально для каждого символа
- Использует `db.get_accum_events(symbol, window_sec)`

### Функция `get_fgi_value` (context_service.py:7-24)

- Получает глобальный индекс страха и жадности
- Кэшируется на 30 минут
- Одинаковый для всех монет (правильно)

## Заключение

Проблема была в том, что **FVG статус не вычислялся** и использовалось дефолтное значение для всех монет. После исправления все данные сигналов теперь вычисляются индивидуально для каждой монеты:

- **RSI, MACD, Объем, FVG** - индивидуальные для каждой монеты
- **FGI** - глобальный (правильно)
- **MTF накопление** - индивидуальный для каждой монеты

Система теперь корректно отображает уникальные технические данные для каждой монеты в сигналах.
