## 🎯 ОСНОВНОЕ ПРАВИЛО

### ✅ **ОБЯЗАТЕЛЬНО: Тесты для каждого нового модуля**

**Правило:** При создании любого нового Python модуля (`.py` файла) **ОБЯЗАТЕЛЬНО** создавать соответствующий файл с юнит-тестами.

---

## 📋 ПРАВИЛА И ПРОЦЕСС

### 1. Ответственный за тесты

**Анна (QA Engineer)** — главный ответственный за:

- Создание тестов для новых модулей
- Поддержание покрытия тестами > 80%
- Проверку качества тестов
- Code review тестов

### 2. Когда создавать тесты

#### ✅ ОБЯЗАТЕЛЬНО создавать тесты для:

- **Новых модулей** (любой новый `.py` файл)
- **Новых классов** (если класс критичен)
- **Новых публичных функций** (API endpoints, core functions)
- **Изменений в критичных модулях** (signal_live.py, risk_manager.py, etc.)

#### ⚠️ РЕКОМЕНДУЕТСЯ создавать тесты для:

- Рефакторинга существующего кода
- Исправления багов (регрессионные тесты)
- Новых фич в существующих модулях

### 3. Требования к тестам

#### Минимальные требования:

- ✅ Покрытие > 70% для новых модулей
- ✅ Все публичные функции/методы протестированы
- ✅ Тесты проходят (100% pass rate)
- ✅ Тесты изолированы (используют моки для внешних зависимостей)

#### Желательные требования:

- ✅ Покрытие > 80% для критичных модулей
- ✅ Тесты для edge cases
- ✅ Тесты для error handling
- ✅ Тесты для fallback behavior

### 4. Структура тестов

#### Именование:

- Файл тестов: `test_<module_name>.py`
- Расположение: `tests/unit/test_<module_name>.py`
- Класс тестов: `Test<ClassName>` или `Test<ModuleName>`

#### Пример:

```python
# Модуль: structured_logging.py
# Тест: tests/unit/test_structured_logging.py

class TestStructuredLogging:
    def test_configure_structured_logging(self):
        ...
```

### 5. Процесс создания тестов

#### Шаг 1: Создание модуля

```bash
# Создаёте новый модуль
touch new_module.py
```

#### Шаг 2: Создание тестов (ОБЯЗАТЕЛЬНО!)

```bash
# Сразу создаёте тесты
touch tests/unit/test_new_module.py
```

#### Шаг 3: Написание тестов

- Минимум: тесты для всех публичных функций
- Идеально: тесты для всех функций + edge cases

#### Шаг 4: Проверка

```bash
# Запускаете тесты
pytest tests/unit/test_new_module.py -v

# Проверяете покрытие
pytest tests/unit/test_new_module.py --cov=new_module --cov-report=term-missing
```

#### Шаг 5: Commit

```bash
# Коммитите модуль И тесты вместе
git add new_module.py tests/unit/test_new_module.py
git commit -m "feat: Add new_module with tests"
```

## 🎯 ПРИМЕРЫ

### ✅ ХОРОШИЙ ПРИМЕР:

```bash
# 1. Создали модуль
touch prometheus_metrics.py

# 2. СРАЗУ создали тесты
touch tests/unit/test_prometheus_metrics.py

# 3. Написали код и тесты
# 4. Проверили покрытие
pytest tests/unit/test_prometheus_metrics.py --cov=prometheus_metrics

# 5. Закоммитили вместе
git add prometheus_metrics.py tests/unit/test_prometheus_metrics.py
git commit -m "feat: Add Prometheus metrics with tests"
```

### ❌ ПЛОХОЙ ПРИМЕР:

```bash
# 1. Создали модуль
touch new_module.py

# 2. НЕ создали тесты (❌ НАРУШЕНИЕ ПРАВИЛА!)

# 3. Закоммитили без тестов
git add new_module.py
git commit -m "feat: Add new module"  # ❌ БЕЗ ТЕСТОВ!
```

## 🚨 НАРУШЕНИЯ ПРАВИЛА

### Если модуль создан без тестов:

1. **Немедленно** создать тесты
2. Добавить в TODO список
3. Анна проверяет и добавляет тесты если нужно

### Если тесты не проходят:

1. **Немедленно** исправить
2. Не коммитить код с падающими тестами
3. Если тест падает из-за бага - исправить баг, не удалять тест

## 📝 ЧЕКЛИСТ ДЛЯ РАЗРАБОТЧИКОВ

Перед коммитом нового модуля проверьте:

- [ ] Создан файл `tests/unit/test_<module_name>.py`
- [ ] Все публичные функции имеют тесты
- [ ] Тесты проходят (`pytest tests/unit/test_<module_name>.py`)
- [ ] Покрытие > 70% (`--cov` показывает > 70%)
- [ ] Тесты используют моки для внешних зависимостей
- [ ] Тесты изолированы (не зависят от других тестов)
- [ ] Тесты и модуль закоммичены вместе
