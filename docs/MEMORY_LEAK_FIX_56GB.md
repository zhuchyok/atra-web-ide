# Исправление утечки памяти (Python ~56 ГБ)

## Причина

Один Python-процесс (скорее всего **Victoria** в контейнере `victoria-agent`) потреблял десятки гигабайт из‑за неограниченного роста структур в памяти:

1. **CollectiveMemorySystem** (`knowledge_os/app/collective_memory.py`)
   - При каждом действии Victoria вызывается `record_action(..., result=..., location=...)`.
   - `result` — полный текст ответа LLM (до сотен KB на запрос).
   - `self.traces[location]` — список следов по location без лимита.
   - Количество location (категории, задачи) тоже не ограничивалось.
   - Итог: неограниченный рост `traces` и объёма данных в них → десятки ГБ.

2. **IsolatedContext** (`knowledge_os/app/isolated_context.py`)
   - `memory` — список сообщений без ограничения длины.

## Внесённые изменения

### collective_memory.py

- **MAX_TRACES_PER_LOCATION** (по умолчанию 200) — в каждой location хранятся только последние N следов.
- **MAX_TRACE_RESULT_CHARS** (по умолчанию 2000) — в памяти хранится только начало `result`, длинный текст обрезается.
- **MAX_TRACE_LOCATIONS** (по умолчанию 500) — максимум ключей в `self.traces`; при превышении удаляется самая старая location.

Переменные окружения (опционально):

- `COLLECTIVE_MEMORY_MAX_TRACES_PER_LOCATION`
- `COLLECTIVE_MEMORY_MAX_RESULT_CHARS`
- `COLLECTIVE_MEMORY_MAX_LOCATIONS`

## Подробнее: лимит 2000 символов на `result`

### Что такое `result`

При каждом завершённом действии Victoria (решить задачу, выполнить план и т.д.) вызывается:

```python
await self.collective_memory.record_action(
    agent_name="Виктория",
    action="solve",
    result=result.get("result", ""),  # ← полный текст ответа LLM
    location=category
)
```

**`result`** — это **полный текст ответа модели**: план, отчёт, код, объяснение. Один такой ответ может быть 5 KB, 50 KB или 500 KB. Раньше этот текст целиком сохранялся в каждом «следе» (trace) в оперативной памяти и в БД, что и давало рост потребления памяти до десятков ГБ.

### Что делает лимит 2000 символов

Перед созданием объекта следа в памяти мы обрезаем строку:

- если `result` — строка длиннее 2000 символов → в след попадает `result[:2000] + "..."`;
- иначе в след попадает весь `result`.

То есть в **оперативной памяти** в каждом trace хранится не больше ~2 KB текста результата вместо десятков/сотен KB.

### На что это влияет

| Где используется `result`                                                        | До лимита                                                    | После лимита                                                                                                                              |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **RAM (трасси в памяти)**                                                        | Полный ответ (до сотен KB на след)                           | Не больше 2000 символов (~2 KB) на след → сильное снижение потребления памяти.                                                            |
| **Контекст для других агентов** (`get_environmental_context` → `recent_actions`) | В контекст и так отдавалось только `str(trace.result)[:200]` | По-прежнему отдаётся 200 символов на след. Поведение не меняется.                                                                         |
| **Агрегированные паттерны** (`successful_patterns`)                              | Использовалось `str(trace.result)[:100]`                     | По-прежнему 100 символов. Без изменений.                                                                                                  |
| **БД** (`environmental_traces`)                                                  | В таблицу писался полный `result`                            | В таблицу пишется `str(trace.result)[:1000]` (уже обрезанный в памяти до 2000, в БД — до 1000). В БД хранится «выжимка», не полный ответ. |

Итог:

- **Лимит нужен в первую очередь для RAM**: меньше данных в каждом trace → меньше общий объём трасс в памяти.
- **На логику «что видят агенты» и «какие паттерны» почти не влияет**: там и так используются короткие срезы (100–200 символов). Меняется только то, что мы не держим в памяти и не пишем в БД «хвост» длинного ответа.
- **Полный ответ пользователю** по-прежнему отдаётся в момент ответа Victoria; обрезка касается только того, что **сохраняется** в Collective Memory (в памяти процесса и в БД).

Изменить порог можно через переменную окружения `COLLECTIVE_MEMORY_MAX_RESULT_CHARS` (по умолчанию 2000).

## Полный текст не теряется: БД как «переходное» хранилище

Идея «полный текст где-то сохранить, но не в памяти, и потом при желании очистить» в коде реализована так (по мировым практикам):

### Как сделано сейчас

1. **В памяти процесса** — в каждом trace хранится только обрезка (до 2000 символов). Так мы не раздуваем RAM.
2. **В БД** (`environmental_traces.result`, тип `TEXT`) — при сохранении следа в БД пишется **полный** `result` без обрезки. То есть «мысль» не теряется: полный ответ лежит в БД.
3. **Очистка** — можно настроить политику хранения: например, периодически удалять строки старше N дней (retention), чтобы БД не росла бесконечно. Сама таблица и есть «переходное» хранилище: полный текст там есть, пока строку не удалили по политике.

Итого: полный текст **не в памяти**, а **в БД**; в памяти только короткий превью. При необходимости полный результат можно прочитать из БД по `trace_id`.

### Вариант с временным файлом (опционально)

Если бы полный текст нужно было держать именно в **файле**, а не в БД, типичный подход такой:

- При `record_action`: полный `result` записать во временный файл (например `COLLECTIVE_MEMORY_TEMP_DIR/{trace_id}.txt`), в память положить только обрезку (и при необходимости путь к файлу или `trace_id`).
- При сохранении в БД: прочитать файл, записать в `environmental_traces.result`, затем **удалить файл** — т.е. «после решения/отправки» файл очищается, полный текст остаётся только в БД.
- Дополнительно: фоновый job раз в N часов удаляет оставшиеся файлы старше N часов (на случай сбоев).

Сейчас выбран вариант «полный текст сразу в БД», без промежуточного файла: проще, меньше движущихся частей, и БД уже есть. Вариант с временным файлом можно добавить позже, если появятся требования (например, очень большие ответы или отдельный процесс записи в БД).

### collective_memory.py (дополнительно, причина 56 ГБ)

- **MAX_AGENT_MEMORIES** (по умолчанию 100) — максимум агентов в `agent_memories`; при превышении удаляется самый «старый» агент. Раньше словарь рос неограниченно.
- **MAX_EXPERIENCE_VALUE_CHARS** (по умолчанию 2000) — строковые значения в `experience` при `update_individual_memory` обрезаются до этого размера.

Переменные окружения: `COLLECTIVE_MEMORY_MAX_AGENTS`, `COLLECTIVE_MEMORY_MAX_EXPERIENCE_CHARS`.

### isolated_context.py

- **MAX_MEMORY_ENTRIES = 100** — в контексте хранятся только последние 100 сообщений.
- **MAX_CONTEXTS** (по умолчанию 200) — максимум контекстов в `ContextManager.contexts`; при превышении удаляется контекст с самым старым `last_accessed`. Раньше словарь рос неограниченно (каждый уникальный agent+project = новый контекст).
- **MAX_MESSAGE_CONTENT_CHARS** (по умолчанию 2000) — при `add_memory` содержимое сообщения обрезается до этого размера (полный ответ LLM не хранится в памяти контекста).

Переменные окружения: `ISOLATED_CONTEXT_MAX_CONTEXTS`, `ISOLATED_CONTEXT_MAX_MESSAGE_CHARS`.

## Что сделать после правок (обязательно)

**Чтобы ограничения применились, процесс Victoria должен быть перезапущен.** Если не перезапустить, старый процесс без лимитов продолжит работать — память останется на уровне 56 ГБ.

```bash
docker-compose -f knowledge_os/docker-compose.yml restart victoria-agent
```

После перезапуска рост потребления памяти процессом Victoria должен существенно замедлиться; при длительной работе — стабилизироваться в разумных пределах.

### Проверка, что лимиты применены

- В логах Victoria при eviction появятся сообщения вида: `🗑️ [MEMORY] Evicted agent ...` или `🗑️ [MEMORY] Evicted context ...`.
- Мониторинг памяти: `docker stats victoria-agent` или Grafana (порт 3002). Через 1–2 часа после рестарта потребление должно стабилизироваться, а не расти линейно.

### Если память всё ещё высокая после рестарта

1. Убедиться, что контейнер действительно перезапущен (`docker ps`, время старта контейнера).
2. Снизить лимиты через env в `docker-compose` или `.env`: например `COLLECTIVE_MEMORY_MAX_LOCATIONS=100`, `COLLECTIVE_MEMORY_MAX_TRACES_PER_LOCATION=50`, `ISOLATED_CONTEXT_MAX_CONTEXTS=50`.
3. Проверить другие источники: кэш моделей MLX (`MLX_MAX_CACHED_MODELS`), semantic_cache/embedding_optimizer (лимиты уже есть), количество воркеров.

## Retention для environmental_traces

Чтобы таблица `environmental_traces` не росла бесконечно, можно периодически удалять старые записи.

**Скрипт:** [knowledge_os/scripts/cleanup_old_traces.py](knowledge_os/scripts/cleanup_old_traces.py)

- Удаляет следы старше N дней (по умолчанию 90).
- Переменные окружения: `DATABASE_URL`, `TRACES_RETENTION_DAYS` (по умолчанию 90).

**Запуск вручную:**

```bash
cd knowledge_os/scripts && python cleanup_old_traces.py
```

**По расписанию (cron, раз в сутки):**

```bash
0 3 * * * cd /path/to/atra-web-ide/knowledge_os/scripts && TRACES_RETENTION_DAYS=90 DATABASE_URL=postgresql://admin:secret@localhost:5432/knowledge_os python cleanup_old_traces.py
```

(Путь и DATABASE_URL подставить под свой хост; по умолчанию retention 90 дней.)

## Мониторинг памяти

- **Контейнер Victoria:** потребление RAM смотреть в `docker stats victoria-agent` или в Activity Monitor (процесс Python в контейнере).
- **Prometheus/Grafana:** метрика потребления памяти процесса Victoria — `container_memory_usage_bytes` по контейнеру `victoria-agent` (или аналог). Чтобы метрика была в Prometheus, нужен сбор с Docker: cAdvisor или node_exporter с docker socket; см. [docs/GRAFANA_SETUP.md](GRAFANA_SETUP.md). Grafana Web IDE — порт 3002. При необходимости можно экспортировать из приложения Victoria кастомную метрику (например `process_resident_memory_bytes` через Prometheus client).
- **Сводка лимитов (что включено):** Collective Memory — MAX_TRACES_PER_LOCATION, MAX_TRACE_RESULT_CHARS, MAX_TRACE_LOCATIONS, MAX_AGENT_MEMORIES, MAX_EXPERIENCE_VALUE_CHARS; IsolatedContext — MAX_MEMORY_ENTRIES, MAX_CONTEXTS, MAX_MESSAGE_CONTENT_CHARS; воркер — автосброс зависших in_progress (SMART_WORKER_STUCK_HOURS).
- После включения лимитов рост памяти должен стабилизироваться в разумных пределах; при подозрении на рост — перезапуск Victoria и проверка логов.
