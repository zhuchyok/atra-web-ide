## 1. Архитектурная целостность

Проект представляет собой современное Fullstack-приложение:

- **Frontend:** Nuxt 4 (Vue 3, TypeScript, Tailwind CSS). Использует Pinia для управления состоянием заказа и конфигурации дилера.
- **Backend (Proxy):** Nuxt Server Routes (`server/api/`). Обрабатывает отправку email через Nodemailer и проксирует заказы в основное API.
- **Core API:** `moskit-api` на **Rust (Axum + SQLx + PostgreSQL)**. Обеспечивает высокую производительность и типизацию.
- **Мультитенантность:** Реализована через `useTenantStore`, подгружающий конфиг дилера (цвета, контакты, цены) через API.

**Выявленные риски:**

- [x] В `server/api/orders.post.ts` сохранение в БД обернуто в `try-catch` без блокировки ответа пользователю. Это хорошо для UX (email уходит), но может привести к потере данных в БД при сбое `moskit-api`.
- [ ] TODO: Маппинг позиций заказа (`items: []`) в Rust API пока не реализован полностью (стоит заглушка).

## 2. Layout Stability (CLS)

- **Hero-секции:** На страницах товаров (например, `antikoshka/index.vue`) внедрены жесткие ограничения `min-h-[440px]` и `items-stretch`. Это предотвращает «прыжки» контента при загрузке изображений.
- **Изображения:** Используется компонент `HeroImage` с заданными `width` и `height`, что является мировой практикой для стабильности верстки.
- **Шрифты:** Подключены через `@fontsource`, что минимизирует задержку отрисовки текста.

---

## 3. SEO & Мета-данные

- **Динамические заголовки:** Используется `computed` для формирования `title` и `description` с учетом города и имени дилера.
- **Микроразметка:** Внедрена поддержка `schema.org` (Product, FAQPage, AggregateOffer). Это критично для ранжирования в Google и Яндекс.
- **Sitemap:** В корне проекта присутствуют `sitemap.xml` и специализированные карты для внутренних страниц и изображений.

## 4. Безопасность (Victoria Special)

- **Экранирование:** В `server/api/orders.post.ts` используется `escapeHtml` для всех полей, вставляемых в HTML-письмо. Защита от XSS через email подтверждена.
- **Валидация телефонов:** Реализована многоуровневая проверка:
  1. На фронтенде (`OrderForm.vue`): маска ввода, блокировка нецифровых символов, regex.
  2. На бэкенде (`orders.post.ts`): нормализация (замена 8 на 7) и жесткая проверка на 11 цифр.
- **Персональные данные:** Чекбокс согласия с политикой конфиденциальности обязателен для отправки формы.

## 6. Интеграция с Knowledge OS: проекты, RAG и «тупеж»

_(Дополнение от 2026-02-23: проверка таблицы проектов, RAG и промптов экспертов.)_

### 6.1 Таблица `projects`

- **setki-21** присутствует: `slug = setki-21`, `workspace_path = /workspace/dev/setki-21`, `is_active = true`.
- Путь корректен для контекста агентов (workspace внутри контейнера/сервера).

### 6.2 RAG (knowledge_nodes)

- В **knowledge_nodes** нет колонки `project_id`. Связь с проектом только через метаданные: `metadata->>'file_path'` (полный путь к файлу) и `source` (например `indexing_daemon`).
- Найден **34 узла**, у которых в `metadata` или `source_ref` встречается «setki» (файлы из setki-21 или путей, содержащих setki).
- **Проблема:** при выборке RAG в `ai_core._get_knowledge_context_impl` и в `knowledge_service._get_knowledge_context` **не передаётся и не используется project_context**. Запрос идёт по всем доменам (AI Research, victoria_tasks, project_files и т.д.) без фильтра по проекту. В результате в контекст могут попадать узлы из atra-web-ide и других проектов, что размывает ответы по setki-21.

### 6.3 Промпты экспертов

- Системные промпты экспертов хранятся в БД (`experts.system_prompt`). В выборочно проверенных промптах **нет явных инструкций** вида «используй список проектов», «ищи только в контексте проекта X» или «при запросе по проекту фильтруй знания по project_context».
- `project_context` передаётся в оркестрацию, задачи и долгосрочную память, но **не в вызов RAG** и не в формулировки системных промптов экспертов как обязательное правило «сначала определи проект, потом ищи по нему».

### 6.4 Вероятные причины «тупежа» (путаница контекста)

1. **RAG не привязан к проекту** — при запросе в контексте setki-21 в контекст модели подмешиваются знания из всех проиндексированных файлов (в т.ч. atra-web-ide), что даёт смесь контекстов и противоречивые подсказки.
2. **Нет явной инструкции «сначала проект»** — модель не получает жёсткого указания: «текущий проект — setki-21; при поиске по коду/документам учитывай только этот проект».
3. **Разные источники контекста** — долгосрочная память и задачи фильтруются по `project_context`, а RAG — нет; рассинхрон усиливает путаницу.

### 6.5 Рекомендации

1. **[x] Скорректировать RAG под проект:** при вызове `_get_knowledge_context` передавать `project_context` (например slug `setki-21`) и в запросе к `knowledge_nodes` фильтровать по `metadata->>'file_path'` (например `LIKE '%/setki-21/%'` или хранить в metadata `project_slug` и фильтровать по нему). Альтернатива: отдельный домен/подпространство на проект.
2. **[x] Единый project_context в цепочке:** убедиться, что один и тот же `project_context` передаётся из API/чата в оркестратор, в вызов RAG и в системный промпт (например, одна строка в системном промпте: «Текущий проект: {project_context}. Ответы и поиск по коду/документам — только в рамках этого проекта.»).
3. **[x] Индексация setki-21:** проверить, что файлы из `workspace_path` setki-21 реально индексируются (indexing_daemon или скрипт по `projects.workspace_path`) и в `metadata` есть либо путь, содержащий setki-21, либо явный `project_slug`.
4. **[x] Аудит промптов:** добавить в шаблоны/системные промпты экспертов короткий блок про использование текущего проекта (и при необходимости — списка проектов из `projects`) для поиска и ответов. _Реализовано: в ai_core при сборке role-aware промпта (Query Orchestrator) к шаблону роли дописывается строка «Если в запросе указан текущий проект — используй для поиска и ответов только контекст этого проекта.» при заданном project_context._

### 6.6 Внедрённые изменения (2026-02-23)

- **RAG:** В `ai_core._get_knowledge_context_impl` и `knowledge_service._get_knowledge_context` добавлен параметр `project_context`; при его указании узлы из `project_files`/`indexing_daemon` фильтруются по `metadata->>'project_slug'` или `metadata->>'file_path' LIKE '%' || project_context || '%'`.
- **Цепочка project_context:** В `run_smart_agent_async` / `run_smart_agent_async_impl` добавлен аргумент `project_context`; он передаётся в оба вызова `_get_knowledge_context` и в промпт. В `execute_assignments` и в `victoria_enhanced` (solve → \_request_project_context, три вызова `run_smart_agent_async`) контекст проекта передаётся в ai_core.
- **Промпт:** При заданном `project_context` в начало промпта добавляется строка: «Текущий проект: {project_context}. Ответы и поиск по коду/документам — только в рамках этого проекта.»
- **Индексация:** В `indexing_daemon` при индексации файла по таблице `projects` определяется `project_slug` (по `workspace_path` или вхождению slug в путь) и записывается в `metadata` узла.

### 6.7 Проверка цепочки: entry points → RAG → индексация → промпты (2026-02-23)

**Проверено:**

1. **Точки входа:** `victoria_server` читает `body.project_context`, валидирует по реестру, кладёт в `context_with_history["project_context"]` и передаёт в Enhanced. Backend `POST /api/chat/ask-victoria` передаёт `body.project_context` в VictoriaClient. Telegram-сессия хранит `project_context`, команда `/project` переключает контекст.
2. **RAG:** В `ai_core._get_knowledge_context_impl` при заданном `project_context` узлы из `project_files`/indexing_daemon фильтруются по `metadata->>'project_slug' = $2` или `metadata->>'file_path' LIKE '%' || $2 || '%'`.
3. **Индексация:** `indexing_daemon` по таблице `projects` определяет `project_slug` по пути и пишет в `metadata` узла. `index_cognitive_code.py` при `--project` / `INDEX_PROJECT_CONTEXT` пишет `project_context` в metadata (домен AI Research без проектного фильтра по дизайну).
4. **Промпт:** В `run_smart_agent_async_impl` при заданном `project_context` в начало промпта добавляется блок «Текущий проект: {project_context}. Ответы и поиск по коду/документам — только в рамках этого проекта.»

**Исправленный разрыв:**

- **Делегирование подзадач:** Раньше `execute_task_assignment` в `task_distribution_system_complete` вызывал `run_smart_agent_async` без `project_context`, поэтому подзадачи выполнялись в контексте MAIN_PROJECT (atra-web-ide), а не запрошенного проекта (например setki-21).
- **Внесённые изменения:** В `execute_task_assignment` добавлен аргумент `project_context`; он передаётся в `run_smart_agent_async`. В `victoria_enhanced` при выполнении назначений передаётся `_request_project_context`. Для синтеза по отделам используется сохранённый `_project_context` на экземпляре TaskDistributionSystem.

**Итог:** Цепочка от точки входа до RAG, индексации и промпта проверена; разрыв при делегировании подзадач устранён.
