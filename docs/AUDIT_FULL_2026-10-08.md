### 5. [P1] Universal gate (v149.26) под нагрузкой деградирует молча: /api/tags MLX падает 15/24

- **Симптом (нагрузочный тест 50с, 10×phi3.5@11434 + 6×fast@11435):** tags 11434: 24/24 OK, p50=2ms p95=5ms; tags 11435: **15 отказов из 24**, p95=1660ms; генерации 11435: **0 OK / 753 ошибки**; генерации 11434: ни одна не завершилась за 50с (phi3.5 грузится >120с — см. нах. 3).

### 6. [P1] Рецидив v149.16: ORDER BY выражения над `<=>` убивает HNSW в проектном RAG-пути и semantic cache

- **Симптом:** живые запросы 1.7с, один с wait_event=LockManager 6.7с; 63 активных соединения PG.
- **Цепочка (EXPLAIN ANALYZE, живьём):** `ORDER BY (1-(embedding <=> $1)) DESC LIMIT n` + фильтр `(metadata->>'project_slug'=$2 OR …)` → **Parallel Seq Scan по ~100 315 строкам** + top-N heapsort — индекс не используется, потому что сортируется выражение, а не индексный оператор. Тот же паттерн в `semantic_ai_cache` (кэшlookup!). Плюс 12+ параллельных `typeinfo_tree` (churn соединений от перезапусков флота).
- **Связи:** каждый RAG-поиск сканирует 100k векторов → CPU/LWLock-давление → замедление воркеров → срабатывание «спасателей» (урок v149.22). Растёт вместе с базой.
- **Решение:** как в v149.16: ORDER BY `embedding <=> $1` (индексный), штраф/фильтры — в Python-реранке; для проектного пути — частичный HNSW-индекс по проекту или pre-filter по GIN+ограничение кандидатов; в semantic_ai_cache — то же.
- **Верификация:** EXPLAIN показывает Index Scan using HNSW; p95 запроса <150мс; ноль LockManager-ожиданий за час пиковой нагрузки.
- **Профилактика:** правило: «любой ORDER BY над embedding — только голый `<=> $1`; проверять EXPLAIN-ом в PR».

- **Симптом:** `docker events` за 20:00–21:40Z — пусто (ноль событий при 5+ рестартах!); `docker logs --since` у vector_core и оркестратора — 0 строк после рестарта демона (у watchdog и др. — живы); Прометей оба инстанса 12/12 UP, хоть генерации MLX мертвы и vector_core unhealthy.
- **Цепочка:** Docker Desktop 29.6.1: после рестарта демона часть контейнеров пишет в оборванные лог-пайпы; история events не переживает рестарт. Health-экспортёры меряют «процесс жив», а не «функция работает».
- **Связи:** из-за этого невозможно атрибутировать рестарт флота 21:15Z (пришлось строить вероятностную цепочку по сторонним логам) — форензика инцидентов стоит часы.
- **Решение:** (а) после рестарта демона — `docker compose restart` «молчаливых» контейнеров (в чек-скрипт из нах. 7); (б) журнал рестартов вести на хосте (обёртка над docker API: кто/когда/почему перезапущен); (в) добавить генерационные канарейки (нах. 2) и vector_core-зонд в метрики.
- **Верификация:** при следующем тест-рестарте демона: events непустые (или задокументированное ограничение), все контейнеры логируют.
- **Профилактика:** «UP ≠ WORKS»: каждый health-check обязан проверять функцию (1 токен LLM, 1 encode, 1 SELECT).

### 13. [P2] Диск Data 89% (208Gi free) — в шаге от порога аварийной чистки

- **Симптом:** `/System/Volumes/Data` 1.6Ti из 1.8Ti (89%). Docker: образы 119.2GB (reclaimable 87MB), контейнеры 10.4GB, volumes 13.8GB.
- **Цепочка:** рост дают: 44 образа, бэкапы pg*dump→GDrive (локальные копии), модели, 20MB+ логи. performance-watchdog при >90% начнёт `rm -rf /tmp/duckdb*_ cache/_` — emergency-чистка в непредсказуемый момент.
- **Связи:** бэкапы 03:00 и батлы ночью — упрутся в диск первыми.
- **Решение:** планка чистки: `docker image prune -a --filter "until=720h"` для неиспользуемых, ротация старых бэкапов, лимиты json-file логов (`max-size: 50m, max-file: 3` в compose x-logging).
- **Верификация:** df <80% и стабилен неделю (монитор в morning report).
- **Профилактика:** аларм на 85%, а не 90%.

### 14. [P3] Дублирование ночного learner и двойной запуск brain-keepalive

- **Симптом:** cron 03:00 `docker exec victoria-agent nightly_learner.py` + контейнер knowledge_nightly (`python -u nightly_learner.py`, NIGHTLY_LOOP=1, интервал 86400) — один и тот же learner двумя путями (библия v149.17: «полумера, в бэклоге» — всё ещё открыто). В 23:05:43 и 23:10:53 brain_keepalive.log — по ДВЕ одновременных строки LOAD FAILED = два экземпляра кипера параллельно.
- **Цепочка:** двойной проход learner по ночам = двойная нагрузка на мозг в окно батлов; двойной кипер = двойные рестарты Ollama.
- **Решение:** оставить контейнер single-pass (cron-строку 03:00 удалить); найти второй источник кипера (`launchctl print` по метке, вероятно дублирующая джоба или скрипт виктории).
- **Верификация:** за ночь один прогон learner (один набор логов), одна строка keepalive на событие.
- **Профилактика:** реестр акторов (см. итог) — при добавлении джобы проверять реестр на дубли.

### 15. [P3] База знаний: 99.6% узлов без типа, машинный мусор вырос

- **Симптом (SQL, живьём):** 101 315 узлов; 100 892 без `metadata->>'node_type'`; «источники недоступны» 3 814 (было 2 890 на v149.17 — РАСТЁТ); «Ошибка парсинга» 835; <10 символов 449.
- **Цепочка:** входной INGESTION_GATE в shadow-режиме (`INGESTION_GATE_ENFORCE_PERCENT=0`) — мусор продолжает писаться; понижение low_priority (v149.17) не останавливает приток.
- **Связи:** загрязняет RAG-выборку (слой 7) и раздувает seq-scan (нах. 6).
- **Решение:** включить enforce постепенно (5→25→100%), чистку «источники недоступны» сделать recurring (раз в неделю), типизацию 100k узлов — отдельной задачей с батчами.
- **Верификация:** счётчики мусора не растут неделю; доля untyped <50% через месяц.
- **Профилактика:** дашборд «здоровье базы знаний» в утреннем отчёте (счётчики мусора).

### 16. [P3] Слой 2 — остаточная карта (без отдельных корней, зафиксировано)

### Правила-уроки (дополнение к библии)

1. «При миграции модели X на слот Y — ревизия ВСЕХ стражей слота в тот же коммит» (урок нах. 1, цена: 5 суток деградации).

4. «Фолбэк маршрутизации логируется как WARN с причиной» (нах. 5).
5. «ORDER BY над embedding — только голый `<=> $1`; EXPLAIN в PR» (нах. 6, рецидив v149.16).
6. «Env модели — один источник (plist); setenv-дубли запрещены» (нах. 9).
7. «После рестарта Docker-демона — контрольный обход: логи/events/unhealthy» (нах. 7, 12).

### Топ-3 системных риска на месяц

1. **RAM-бюджет пересубскрибирован** (Docker VM 32GB wired + MLX-резиденты ~20GB + мозг 30GB + KV@32K ≈ >128GB при нагрузке) — следующий тяжёлый батл может повторно уложить Docker-демон/хост. Требует явного бюджета памяти и ctx=16K (волна 1).
