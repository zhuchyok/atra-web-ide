# 🔍 Анализ причин падения MLX Server и решение

## ❌ Причины падения (анализ логов)

### 1. **Перегрузка при параллельных запросах**

**Проблема:**

- При одновременных запросах от сотрудников (София + Алексей) сервер получает 2+ параллельных запроса
- Каждый запрос может загружать модель в память
- При синтезе результатов Victoria делает еще несколько запросов
- Итого: 4-6 параллельных запросов одновременно

**Логи:**

```
19:19:52 - Задача назначена София
19:19:52 - Задача назначена Алексей
19:19:52 - Синтез результатов (Victoria)
19:19:52 - MLX Server: "All connection attempts failed"
```

**Причина:** Превышение лимита параллельных запросов (5) или нехватка памяти при загрузке моделей.

### 2. **Нехватка памяти (OOM)**

**Проблема:**

- Предзагрузка моделей: ~30GB RAM (qwen2.5-coder:32b, phi3.5:3.8b, tinyllama:1.1b-chat)
- При параллельных запросах может потребоваться загрузка дополнительных моделей
- Mac Studio M4 Max: 128GB RAM, но при высокой нагрузке возможна нехватка

**Признаки:**

- Сервер падает без ошибок в логах
- Процесс завершается с кодом 1
- Health check перестает отвечать

### 3. **Отсутствие supervision**

**Проблема:**

- Сервер запускается вручную
- При падении не перезапускается автоматически
- Нет мониторинга состояния процесса
- Нет защиты от каскадных сбоев

## ✅ Решение: Мировые практики

### 1. **Supervision Pattern (Elixir/OTP)**

**Принцип:** Иерархическая структура процессов с автоматическим перезапуском.

**Реализация:**

- `MLXServerSupervisor` - supervisor для MLX API Server
- Автоматический перезапуск при обнаружении падения
- Rate limiting: максимум 5 перезапусков за 5 минут
- Отслеживание состояния процесса

**Преимущества:**

- Автоматическое восстановление без вмешательства
- Защита от бесконечных циклов перезапуска
- Мониторинг состояния в реальном времени

### 2. **Circuit Breaker Pattern**

**Принцип:** Защита от каскадных сбоев.

**Реализация:**

- Интеграция с `CircuitBreaker`
- После 5 неудачных перезапусков → Circuit OPEN
- Блокировка перезапусков на 60 секунд
- Автоматический переход в HALF_OPEN для тестирования

**Состояния:**

- **CLOSED**: Нормальная работа
- **OPEN**: Слишком много ошибок, перезапуски заблокированы
- **HALF_OPEN**: Тестирование восстановления

**Преимущества:**

- Предотвращает бесконечные циклы перезапуска
- Дает время системе восстановиться
- Снижает нагрузку на систему

### 3. **Exponential Backoff**

**Принцип:** Постепенное увеличение задержки между перезапусками.

**Реализация:**

- Начальная задержка: 2 секунды
- Максимальная задержка: 60 секунд
- Формула: `delay = min(2 * 2^n, 60)`

**Преимущества:**

- Предотвращает перегрузку при частых падениях
- Дает время системе восстановиться
- Оптимизирует использование ресурсов

### 4. **Health Monitoring**

**Принцип:** Постоянная проверка здоровья сервера.

**Реализация:**

- Health check каждые 10 секунд
- Проверка `/health` endpoint
- После 3 неудачных проверок → сервер считается упавшим
- Автоматический перезапуск при обнаружении падения

**Преимущества:**

- Быстрое обнаружение падений
- Предотвращение использования неработающего сервера
- Автоматическое восстановление

### 5. **Graceful Shutdown**

**Принцип:** Корректное завершение процесса.

**Реализация:**

- Отправка SIGTERM для graceful shutdown
- Ожидание завершения (до 10 секунд)
- Принудительная остановка (SIGKILL) при таймауте
- Очистка ресурсов (модели, соединения)

**Преимущества:**

- Сохранение состояния моделей
- Корректное завершение соединений
- Предотвращение потери данных

## 🚀 Использование

### Автоматический запуск (рекомендуется):

```bash
# Запуск с Supervisor (автоматический перезапуск)
python3 scripts/start_mlx_with_supervisor.py
```

### Интеграция с Victoria:

Supervisor автоматически запускается при старте Victoria, если:

- `MLX_PRELOAD_MODELS` установлен (MLX используется)
- MLX Server не отвечает на health check

### Ручной запуск:

```bash
# Простой запуск (без supervisor)
python3 knowledge_os/app/mlx_api_server.py
```
