# 🔧 Улучшения устойчивости MLX API Server

## ❌ Найденные проблемы

### 1. **КРИТИЧЕСКАЯ: Несоответствие портов**

- **Проблема**: Сервер запускался на порту `11434`, а клиенты подключались к `11435`
- **Решение**: Исправлен порт на `11435` (можно задать через `MLX_API_PORT`)

### 2. **Отсутствие защиты от перегрузки**

- **Проблема**: Нет ограничения на параллельные запросы
- **Решение**: Добавлен лимит `_max_concurrent_requests = 5`

### 3. **Отсутствие rate limiting**

- **Проблема**: Множественные запросы могли перегрузить сервер
- **Решение**: Rate limiting: `30 запросов/60 секунд` на IP

### 4. **Отсутствие мониторинга памяти**

- **Проблема**: При загрузке нескольких больших моделей возможен OOM
- **Решение**:
  - Мониторинг использования памяти
  - Автоматическая очистка неиспользуемых моделей при `>85%` памяти
  - Блокировка загрузки новых моделей при `>95%` памяти

### 5. **Отсутствие graceful error handling**

- **Проблема**: При ошибках сервер мог упасть
- **Решение**:
  - Обработка `MemoryError` и `RuntimeError`
  - Таймауты для генерации (5 минут)
  - Детальное логирование всех ошибок

### 6. **Отсутствие connection pooling**

- **Проблема**: Каждый запрос создавал новое соединение
- **Решение**: `timeout_keep_alive=120` для переиспользования соединений

## ✅ Реализованные улучшения

### 1. **Исправление порта**

```python
PORT = int(os.getenv("MLX_API_PORT", 11435))  # Было: 11434
```

### 2. **Rate Limiting Middleware**

- Ограничение: `30 запросов/60 секунд` на IP
- Автоматическая очистка старых записей
- HTTP 429 при превышении лимита

### 3. **Защита от перегрузки**

- Лимит параллельных запросов: `5`
- HTTP 503 при превышении
- Мониторинг активных запросов

### 4. **Мониторинг памяти**

```python
def check_memory() -> Dict[str, float]:
    """Проверка использования памяти"""
    memory = psutil.virtual_memory()
    return {
        "used_percent": memory.percent / 100,
        "available_gb": memory.available / (1024**3)
    }
```

### 5. **Автоматическая очистка моделей**

- При `>85%` памяти: предупреждение
- При `>95%` памяти: автоматическая выгрузка неиспользуемых моделей
- Оставляется только последняя использованная модель

### 6. **Graceful Error Handling**

- Обработка `MemoryError` → HTTP 503
- Обработка `TimeoutError` → HTTP 504
- Детальное логирование всех ошибок

### 7. **Connection Pooling**

```python
uvicorn.run(
    app,
    timeout_keep_alive=120,  # Keep-alive для переиспользования
    limit_concurrency=_max_concurrent_requests + 5
)
```

## 📊 Конфигурация

### Переменные окружения:

- `MLX_API_PORT` - порт сервера (по умолчанию: 11435)
- `MLX_API_WORKERS` - количество workers (по умолчанию: 1, т.к. MLX не поддерживает multiprocessing)

### Лимиты:

- **Параллельные запросы**: 5
- **Rate limit**: 30 запросов/60 секунд на IP
- **Таймаут генерации**: 5 минут
- **Memory warning**: 85%
- **Memory critical**: 95%

## 🔍 Диагностика проблем

### Если сервер не отвечает:

1. Проверить порт: `lsof -i :11435`
2. Проверить память: `curl http://localhost:11435/health | jq .memory`
3. Проверить логи на ошибки памяти

### Если превышен rate limit:

- Подождать 60 секунд
- Или использовать разные IP адреса

### Если нехватка памяти:

- Сервер автоматически выгрузит неиспользуемые модели
- Можно вручную перезапустить сервер
