# Почему в Open WebUI не загружается victoria-wisdom-30b

## Если вы выбираете victoria-wisdom-30b:latest и несколько минут нет ответа — сделайте это

1. **Стриминг включён, но точка моргает и текста нет**  
   У модели 30B на Ollama **время до первого токена** может быть **2–4 минуты** даже при прогретой модели. Open WebUI открывает стрим (поэтому точка моргает), но если где‑то в цепочке есть таймаут чтения (например 60–120 с), соединение закрывается до прихода первого байта от Ollama — тогда текст так и не появляется.  
   **Что сделать:** подождать **не меньше 3 минут** без перезагрузки страницы. Если через 3–4 минуты текста всё равно нет — переходите к п. 2 или 3.

2. **Используйте модель «Victoria» вместо «victoria-wisdom-30b:latest»**  
   В списке моделей выберите **Victoria** (источник — OpenAI-совместимый / Victoria Agent), а не «victoria-wisdom-30b:latest» из Ollama. Запрос пойдёт в Victoria Agent; внутри Виктория сама вызывает ту же модель в Ollama, но с другими таймаутами и стримингом. Ответ может появиться стабильнее.

3. **Проверьте, куда уходит запрос**  
   DevTools → Network → отправьте сообщение. Если запрос идёт на **Victoria** (порт 8010), а не на **Ollama** (11434), то задержка из-за пайплайна Виктории (2–5 мин). Для «просто ответ модели» можно создать в Open WebUI отдельное подключение только к Ollama и выбирать модель из него.

4. **Новый чат с коротким вопросом**  
   Длинная история увеличивает время до первого токена. В новом чате задайте один короткий вопрос — если ответ придёт за 1–2 минуты, причина в размере контекста.

---

**В проекте зафиксирована версия Open WebUI v0.8.5** ([releases](https://github.com/open-webui/open-webui/releases)): исправлены бесконечная загрузка при инициализации, падение `/api/models` при неполных метаданных модели, устойчивость к сбоям getModels/getBanners/getTools. После обновления выполните: `docker compose -f knowledge_os/docker-compose.yml pull open-webui && docker compose -f knowledge_os/docker-compose.yml up -d open-webui`.

Open WebUI получает список моделей **только из Ollama** (`OLLAMA_BASE_URL=http://host.docker.internal:11434`). Модель **victoria-wisdom-30b** — кастомная: она не скачивается с ollama.com, а создаётся локально скриптом сборки.

## Возможные причины

### 1. Модель не создана в Ollama
Если вы ни разу не запускали сборку и регистрацию в Ollama, модели в списке не будет.

**Что сделать:** с хоста (не из Docker) из корня проекта:
```bash
# Собрать экспорт (merge адаптеров) и зарегистрировать в Ollama
bash knowledge_os/scripts/assemble_victoria_wisdom.sh
```
Перед этим должны быть: базовая модель (например в `~/mlx-models/qwen2.5-coder-32b`), адаптеры в `training_data/adapters/victoria-wisdom-v1`, путь в скрипте к экспорту корректен. После успешного `ollama create victoria-wisdom-30b ...` модель появится в `ollama list` и в Open WebUI.

### 2. Ollama на хосте недоступен из контейнера
Open WebUI в Docker обращается к Ollama по `host.docker.internal:11434`. Если Ollama не запущен на Mac или слушает другой порт — список моделей будет пустой или старый.

**Проверка с хоста:**
```bash
curl -s http://localhost:11434/api/tags | jq '.models[].name'
```
Должна быть строка с `victoria-wisdom-30b`. Проверка из контейнера:
```bash
docker exec open-webui curl -s http://host.docker.internal:11434/api/tags
```

### 3. Модель есть, но «не отвечает» или «не загружается» (таймаут / ошибка при выборе)

**Почему victoria-wisdom-30b:latest не отвечает в чате:**

1. **Тяжёлая модель (30B):** первый токен при запросе к Ollama может идти 1–3 минуты и больше. Если Open WebUI шлёт **нестриминговый** запрос (ждать весь ответ разом), клиент или прокси может оборвать соединение по таймауту (в части версий Open WebUI дефолт ~5 мин, переменная `AIOHTTP_CLIENT_TIMEOUT` не всегда применяется ко всем запросам).
2. **Ollama принимает запрос, но долго молчит** — пока модель считает, буфер не заполняется, и соединение может быть закрыто по таймауту до прихода первого байта.
3. **Нехватка памяти** — Ollama выгружает модель или падает. На Mac Studio с 128 GB обычно достаточно; при проблемах проверьте логи Ollama.

**Что сделать:**

- **Использовать Victoria / Victoria-Enhanced в Open WebUI** (иконка 🔗): запросы идут в Victoria Agent (порт 8010), который сам дергает Ollama/MLX с большими таймаутами и стримингом. Модель «victoria-wisdom-30b» при этом не выбирать в списке — отвечает именно Виктория.
- **В чате включить стриминг** (если есть опция): первый токен может прийти с задержкой, дальше ответ идёт потоком — таймаут по первому байту меньше критичен.
- **Прогреть модель с хоста:** `curl -X POST http://localhost:11434/api/generate -d '{"model":"victoria-wisdom-30b:latest","prompt":"Привет","stream":false}'` — подождать ответа; после прогрева следующий запрос из Open WebUI может пройти быстрее.
- В docker-compose для open-webui уже задано `AIOHTTP_CLIENT_TIMEOUT=1200` (20 мин). После смены перезапустить: `docker compose -f knowledge_os/docker-compose.yml up -d open-webui`.
- **Имя с тегом** — в UI показывается `victoria-wisdom-30b:latest`; в Ollama после `ollama create victoria-wisdom-30b` создаётся тег `:latest`. Если модель создана с другим тегом, в списке будет другое имя.

### 3.1. Модель загружена и прогрета, но ответа нет несколько минут — в чём причина?

Если модель уже в памяти Ollama и прогрета, а ответ в чате так и не появляется, возможны три варианта.

**Вариант A: Запрос идёт в Victoria Agent, а не в Ollama**

Если в Open WebUI выбран источник «Victoria» или запросы чата настроены на OpenAI-совместимый endpoint, то запрос уходит на **Victoria Agent** (порт 8010), а не напрямую в Ollama. В этом случае задержка связана не с прогревом модели, а с пайплайном Виктории:

1. **Стратегия** — вызов LLM (выбор quick_answer / deep_analysis и т.д.).
2. **understand_goal** — ещё один вызов LLM (переформулировка цели).
3. **Выполнение** — Veronica, Enhanced или agent.run (много шагов, каждый с вызовом LLM).

Каждый шаг может занимать 30–90+ секунд. Итого до первого ответа легко набегает **2–5 и больше минут**. Интерфейс при этом может показывать «думает» без частичного ответа, особенно если используется нестриминговый режим или 202 + polling и UI не обновляется.

**Как проверить:** в браузере откройте DevTools → вкладка Network. Отправьте сообщение в чат и посмотрите, на какой адрес уходит запрос: `host.docker.internal:11434` (Ollama) или контейнер с Victoria (например, порт 8010 / open-webui backend). Если запрос идёт на Victoria — задержка из-за пайплайна Виктории.

**Что делать:** для быстрого ответа «просто от модели» выбирайте в Open WebUI именно **модель Ollama** (victoria-wisdom-30b:latest) и убедитесь, что чат ходит в Ollama, а не в Victoria. Либо смириться с задержкой 2–5 мин при использовании Victoria.

**Вариант B: Запрос идёт в Ollama, но без стриминга**

Open WebUI может отправлять в Ollama запрос с `stream: false`. Тогда Ollama сначала генерирует **весь** ответ в памяти и отдаёт его одним блоком. Пока генерация не закончится, в интерфейсе ничего не появляется. Для 30B и ответа в несколько абзацев это может быть **3–7 минут** даже при прогретой модели.

**Что делать:** включите в настройках чата/модели **стриминг** (streaming), если такая опция есть. Тогда первый токен придёт быстрее (обычно 30–90 с для тяжёлой модели), и ответ будет появляться по частям.

**Вариант C: Запрос в Ollama, но огромный контекст**

Если в запрос подставляется длинная история чата и большой системный промпт, объём входа может быть 5–15k токенов. Даже при прогретой 30B обработка такого контекста и генерация первого токена может занимать **2–4 минуты**. Создаётся впечатление, что «модель не отвечает», хотя Ollama просто долго считает.

**Что делать:** попробовать в **новом чате** короткий вопрос (1–2 предложения) без длинной истории. Если в новом чате ответ приходит за 1–2 минуты — причина в размере контекста. Дальше можно сокращать историю в настройках или использовать модель с меньшим контекстом.

**Кратко:** чаще всего «модель прогрета, но несколько минут нет ответа» — это либо запрос идёт в **Victoria** (долгий пайплайн), либо запрос в **Ollama без стриминга** (ответ отдаётся одним блоком в конце), либо **очень большой контекст** в одном запросе.

### 4. Используется только MLX, а не Ollama
Модель **victoria-wisdom-30b** в проекте может работать в двух местах:
- **MLX API Server** (порт 11435) — путь к экспорту задаётся в `mlx_api_server.py` (например `training_data/exported_model`). Этим пользуется Victoria Agent.
- **Ollama** (порт 11434) — сюда модель попадает только после `ollama create` из Modelfile (скрипт `assemble_victoria_wisdom.sh`). Этим пользуется Open WebUI.

Если модель собрана только для MLX и не создана в Ollama — в Open WebUI её не будет.

## Рекомендуемый порядок

1. На хосте: `ollama list` — есть ли `victoria-wisdom-30b`.
2. Если нет — выполнить `bash knowledge_os/scripts/assemble_victoria_wisdom.sh` (предварительно проверить пути к базовой модели и адаптерам).
3. Убедиться, что Ollama запущен и доступен: `curl -s http://localhost:11434/api/tags`.
4. В Open WebUI обновить список моделей (перезагрузка страницы или Admin → Settings → обновление источников).
5. Если модель появляется, но при выборе долго «грузится» — подождать первую загрузку (несколько минут для 30B) или проверить логи Ollama при ошибке.

## «Загрузка…» крутится на всех моделях (модель уже загружена)

Если в списке у модели зелёная точка (модель в памяти Ollama), но под именем модели в чате всё время «Загрузка…» — интерфейс ждёт ответа от бэкенда (запрос к Ollama при выборе модели). Если это происходит **на всех моделях**, возможны:

1. **Запрос из контейнера к Ollama не завершается** (host.docker.internal:11434) — таймаут, сетевая задержка. Проверка: `docker exec open-webui curl -s -o /dev/null -w "%{http_code}" --max-time 5 http://host.docker.internal:11434/api/tags`.
2. **Фронт не снимает состояние загрузки** — известное поведение в части версий: спиннер не исчезает, хотя модель уже отвечает.

**Что сделать:** (1) **Написать сообщение в чат** — часто модель реально отвечает, спиннер просто не обновляется. (2) **Обновить страницу** (F5 или Cmd+Shift+R) после выбора модели — иногда спиннер пропадает. (3) Выбрать **Victoria** или **Victoria-Enhanced** (иконка 🔗) — запросы идут в Victoria Agent, без проверки загрузки в Ollama, спиннер может не показываться. (4) В docker-compose для open-webui добавлен `AIOHTTP_CLIENT_TIMEOUT_MODEL_LIST=30`; после изменений перезапустить контейнер: `docker compose -f knowledge_os/docker-compose.yml up -d open-webui`.

## Слабый интернет не влияет на загрузку модели

**Загрузка victoria-wisdom-30b в Open WebUI идёт полностью локально:** Open WebUI (контейнер) обращается к Ollama на **хосте** (`host.docker.internal:11434`). Модель уже лежит на диске Mac, интернет для запроса «загрузить модель» **не используется**. Слабый или отключённый интернет не может быть причиной бесконечного «Загрузка…». Причина — либо долгая первая загрузка 30B в память (подождать 3–5 мин), либо таймаут/ошибка между контейнером и Ollama. Проверка цепочки: `./scripts/verify_openwebui_ollama.sh`.

## Проверка цепочки Open WebUI → Ollama

Скрипт проверяет доступность Ollama с хоста и из контейнера, наличие модели в списке и при необходимости тестовый запрос:

```bash
./scripts/verify_openwebui_ollama.sh
```

Опционально с прогревом модели (первый вызов может занять несколько минут):

```bash
./scripts/verify_openwebui_ollama.sh --warmup
```

## Альтернатива: не использовать модель в Open WebUI, а вызывать Victoria через инструмент

По архитектуре Singularity 15.0 в Open WebUI можно **не выбирать** локальную модель victoria-wisdom-30b, а использовать любую доступную модель (например qwen2.5-coder:32b или tinyllama) с **инструментом ask_victoria**: тогда запросы к Виктории идут через бэкенд (Victoria Agent на порту 8010), а сама Victoria внутри уже использует victoria-wisdom-30b (Ollama/MLX). См. `docs/OPENWEBUI_SINGULARITY_15_RUNBOOK.md` и `docs/SINGULARITY_15_GOLDEN_PERSONA.md`.
