# Дизайн: верификация деплоя Setki21 и runbook при сбое

**Дата:** 2026-03-06  
**Статус:** Утверждённый дизайн (brainstorm + expert)  
**Связь:** CHANGES §49, SETKI21_SITE_DEPLOY_VDS §7, deploy_setki21_site_vds.sh

---

## 1. Цель и контекст

После деплоя статики Setki21 на VDS пользователь может не видеть обновления: трафик www.setki21.ru иногда идёт не в контейнер **setki21-site**, а в другой бэкенд (например moskit-api), из‑за чего отдаётся старая версия. Нужно:

- **Автоматически** проверять после деплоя, что живой URL отдаёт ту же сборку, что и файлы на VDS (сравнение хэша entry.\*.css в HTML).
- **Runbook** для ручного разбора, если проверка упала: где править маршрутизацию и что проверить (NPM, CDN, DNS).

Подход выбран: проверка в конце скрипта деплоя с возможностью пропуска через `SKIP_SETKI21_VERIFY=1`.

---

## 2. Где править маршрутизацию www.setki21.ru

Маршрутизацию **не** задаёт репозиторий. Её задаёт только **Nginx Proxy Manager (NPM)** на VDS.

| Что                                          | Где                                                                                                                                                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Изменить Forward для www.setki21.ru**      | Веб-интерфейс NPM: **http://45.10.43.248:81** → **Proxy Hosts** → открыть хост с доменом **www.setki21.ru** → вкладка **Details** → **Forward Hostname / IP:** **setki21-site**, **Forward Port:** **80** → Save.               |
| **Образец правильного конфига** (для сверки) | В репо: **scripts/npm_proxy_setki21.conf** — там `set $server "setki21-site"; set $port 80;` и location / идёт в proxy. Реальный конфиг NPM хранит у себя в БД и генерирует nginx сам; файл в репо — образец «как должно быть». |
| **Данные NPM на VDS**                        | Контейнер **atra-nginx-proxy**, volume `./nginx_proxy/data` (из docker-compose). Менять вручную файлы там не рекомендуется — только через UI NPM.                                                                               |

Если после деплоя живой сайт отдаёт старый хэш CSS — первым делом проверить в NPM, что у Proxy Host **www.setki21.ru** в Details указано **setki21-site:80**, а не другой хост.

## 3. Автоверификация в скрипте деплоя

**Место:** конец `scripts/deploy_setki21_site_vds.sh`, после шага 4 (перезапуск setki21-site).

**Логика:**

1. Если задана переменная окружения `SKIP_SETKI21_VERIFY=1` — шаг верификации не выполнять, вывести напоминание про runbook и выйти успешно.
2. Иначе:
   - По SSH на VDS прочитать хэш из `/home/atra/app/setki21_site/index.html`: `grep -o 'entry\.[^"]*\.css'` (первое вхождение).
   - Через `curl -sS` запросить `https://www.setki21.ru/` и из ответа вытащить тот же паттерн (первое вхождение).
   - Если хэши совпадают — вывести OK и выйти 0.
   - Если не совпадают или curl/SSH завершились с ошибкой — вывести явное сообщение: «Верификация не прошла: живой сайт отдаёт другую сборку или недоступен. Runbook: docs/runbooks/SETKI21_DEPLOY_VERIFY_FAIL.md» и выйти с кодом 1.

**Таймаут:** curl не более 15 с. При таймауте считать проверку проваленной (как «не совпадают»).

---

## 4. Runbook при падении проверки

**Файл:** `docs/runbooks/SETKI21_DEPLOY_VERIFY_FAIL.md` (создать).

**Содержание (кратко):**

1. **Симптом:** после `./scripts/deploy_setki21_site_vds.sh` скрипт завершился с ошибкой «Верификация не прошла» или вручную видно, что на сайте старая версия.
2. **Проверить NPM:** открыть http://45.10.43.248:81 → Proxy Hosts → www.setki21.ru → Details. Forward Hostname должен быть **setki21-site**, Port **80**. Если указано иное — исправить на setki21-site:80 и сохранить.
3. **Проверить DNS:** `dig +short www.setki21.ru` должен вернуть 45.10.43.248.
4. **CDN:** если используется Cloudflare/другой CDN — сделать Purge Cache для www.setki21.ru и повторить проверку.
5. **Повторная проверка:** выполнить вручную те же команды, что в скрипте (curl живого URL и SSH grep по index.html), убедиться, что хэши совпадают.
6. **Ссылка на полный чеклист:** docs/SETKI21_SITE_DEPLOY_VDS.md §7.

Runbook не дублирует §7 целиком, а отсылает к нему; в runbook — короткие шаги и **точный адрес, где править NPM** (см. раздел 2 выше).

---

## 5. Обработка ошибок и граничные случаи

- **curl недоступен или таймаут:** считать верификацию проваленной, вывести сообщение и ссылку на runbook, exit 1.
- **SSH недоступен:** то же (проверка после деплоя подразумевает, что SSH уже сработал на шагах 2–4; если на шаге 5 SSH вдруг падает — провал, exit 1).
- **В HTML нет entry.\*.css:** (маловероятно после generate) — считать провалом, exit 1.
- **Деплой с пропуском проверки:** `SKIP_SETKI21_VERIFY=1 ./scripts/deploy_setki21_site_vds.sh` — верификация не выполняется, в конце вывести одну строку: «Верификация пропущена. Проверь вручную: docs/runbooks/SETKI21_DEPLOY_VERIFY_FAIL.md».

---

## 6. Критерии успеха

- После успешного деплоя без `SKIP_SETKI21_VERIFY` скрипт завершается с кодом 0 только если живой https://www.setki21.ru/ отдаёт тот же хэш entry.\*.css, что и index.html на VDS.
- При расхождении или ошибке сети скрипт завершается с кодом 1 и явной ссылкой на runbook.
- В репозитории есть один runbook с пошаговыми действиями и указанием **где править NPM** (URL и путь в UI).
- В дизайн-документе зафиксировано **где искать** настройку маршрутизации: только NPM UI, образец конфига в репо — scripts/npm_proxy_setki21.conf.
