# Управление памятью в MLX API Server

**Дата:** 26.01.2026  
**Проблема:** MLX API Server отключался из-за нехватки памяти

---

## 🔍 Анализ проблемы

### Возможные причины отключения:

1. **Нехватка памяти (OOM - Out of Memory)**
   - Большие модели (70B+) занимают много RAM
   - Несколько моделей загружены одновременно
   - Системный OOM killer убивает процесс

2. **Недостаточная очистка памяти**
   - Старые модели остаются в кэше
   - Нет автоматической выгрузки неиспользуемых моделей
   - Сборка мусора не вызывается принудительно

3. **Отсутствие мониторинга**
   - Нет предупреждений о высоком использовании памяти
   - Нет автоматической очистки при критических значениях

## ✅ Реализованные улучшения

### 1. **Улучшенная функция очистки памяти**

```python
def cleanup_unused_models(aggressive: bool = False):
    """Очистка неиспользуемых моделей при нехватке памяти

    Args:
        aggressive: Если True, выгружает ВСЕ модели (экстренная очистка)
    """
```

**Режимы очистки:**

- **Обычная** (при 85-95%): Оставляет только последнюю модель
- **Экстренная** (при >98%): Выгружает ВСЕ модели
- **Принудительная сборка мусора** после очистки

### 2. **Проверка памяти перед загрузкой моделей**

- Проверка при 85% (предупреждение) → обычная очистка
- Проверка при 95% (критично) → экстренная очистка
- Отказ в загрузке, если после очистки все еще >95%

### 3. **Обработка MemoryError**

- При `MemoryError` при загрузке модели → экстренная очистка
- При `MemoryError` при генерации → экстренная очистка
- Логирование с информацией об использовании памяти

### 4. **Автоматическая очистка в health check**

- Health check проверяет память каждые N секунд
- Автоматически запускает очистку при критических значениях
- Возвращает детальную информацию о памяти

### 5. **Мониторинг памяти**

**Пороги:**

- **Предупреждение:** 85% использования памяти
- **Критично:** 95% использования памяти
- **Экстренно:** 98% использования памяти

**Информация в health check:**

```json
{
  "status": "healthy|warning|critical|degraded",
  "memory": {
    "used_percent": 87.5,
    "available_gb": 12.3,
    "total_gb": 128.0,
    "warning_threshold": 85.0,
    "critical_threshold": 95.0
  }
}
```

## 🛠️ Как это работает

### Сценарий 1: Высокое использование памяти (85-95%)

1. При загрузке модели проверяется память
2. Если >85% → запускается обычная очистка
3. Оставляется только последняя использованная модель
4. Вызывается `gc.collect()` для принудительной сборки мусора

### Сценарий 2: Критическая нехватка памяти (>95%)

1. При загрузке модели проверяется память
2. Если >95% → запускается экстренная очистка
3. Выгружаются ВСЕ модели из кэша
4. Если после очистки все еще >95% → отказ в загрузке

### Сценарий 3: MemoryError при работе

1. Перехватывается `MemoryError`
2. Запускается экстренная очистка (выгружаются все модели)
3. Возвращается HTTP 503 с детальной информацией
4. Процесс продолжает работать (не падает)

### Сценарий 4: Health check мониторинг

1. Health check проверяет память
2. Если >95% → автоматически запускает очистку
3. Возвращает статус "critical" или "warning"
4. Логирует предупреждения

## 🎯 Рекомендации

### 1. **Ограничение количества моделей**

Не загружайте все модели одновременно. Используйте только нужные:

## 🐛 Диагностика проблем

### Проблема: Процесс падает с OOM

**Причина:** Системный OOM killer убивает процесс до того, как Python успевает обработать MemoryError

**Решение:**

1. Уменьшите количество одновременно загруженных моделей
2. Используйте меньшие модели (32B вместо 70B)
3. Увеличьте swap (если возможно)
4. Мониторьте память через health check

### Проблема: Модели не выгружаются

**Причина:** `cleanup_unused_models()` не вызывается или не работает

**Решение:**

1. Проверьте логи на сообщения об очистке
2. Вызовите health check для принудительной очистки
3. Перезапустите сервер

### Проблема: Память растет постепенно

**Причина:** Утечки памяти в MLX или Python

**Решение:**

1. Регулярно вызывайте health check (автоматическая очистка)
2. Перезапускайте сервер периодически
3. Используйте мониторинг памяти
